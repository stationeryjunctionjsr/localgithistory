# Oracle-Specific Choices and Example CRUD

## Oracle-specific choices (performance)

1. **IDENTITY primary keys**  
   All tables use `NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY` for the primary key. No explicit sequences; standard SQL and good for portability.

2. **external_id for API**  
   The legacy `_id` (string) is stored in `external_id VARCHAR2(32)` and is the only identifier exposed in request/response. Numeric `id` is used only for joins and FKs. This avoids leaking internal DB IDs.

3. **Indexes**  
   - Unique on `external_id` for lookup by `_id`.  
   - B-tree on: `sj_users(email)`, `sj_users(phone)`, `sj_orders(user_id)`, `sj_orders(status)`, `sj_orders(created_at)`, `sj_order_items(order_id)`, `sj_sessions(user_id)`, `sj_sessions(refresh_token_id)`, `sj_products(sku)`, `sj_products(is_active)`, and on `created_at` where used for ordering. No composite indexes unless a clear query pattern exists.

4. **CLOB for JSON**  
   Variable or nested data (address, device, cart items, etc.) is stored in CLOB as JSON. Fits all supported Oracle versions; you can move to JSON type on 21c+ later if desired.

5. **Table naming**  
   Prefix `sj_` avoids reserved words (USER, ORDER, DATE, etc.) and keeps object names clear.

6. **Single app user**  
   All access uses one database user (no ADMIN). Parameterized queries only.

## Example CRUD (parameterized)

**Find user by external_id (API _id):**
```sql
SELECT id, external_id, user_id, user_id_formatted, name, email, password_hash,
       role, phone, company_name, address, saved_addresses, is_active,
       approval_status, is_deactivated, credit_limit, credit_used, payment_terms,
       assigned_retailer, created_at, updated_at
FROM sj_users
WHERE external_id = :eid
```

**List orders for a user (by external_id):**  
Resolve user external_id → user id, then:
```sql
SELECT o.id, o.external_id, o.order_number, o.status, o.total, o.created_at, ...
FROM sj_orders o
WHERE o.user_id = :user_id
ORDER BY o.created_at DESC
```

**Order with items (join):**
```sql
SELECT o.*, oi.id AS item_id, oi.product_id, oi.quantity, oi.price
FROM sj_orders o
LEFT JOIN sj_order_items oi ON oi.order_id = o.id
WHERE o.external_id = :order_eid
```
Then resolve `product_id` to `external_id` via `sj_products` for the API.

**Insert user:**
```sql
INSERT INTO sj_users (external_id, user_id, user_id_formatted, name, email, password_hash, ...)
VALUES (:external_id, :user_id, :user_id_formatted, :name, :email, :password_hash, ...)
```

**Update order status:**
```sql
UPDATE sj_orders
SET status = :status, updated_at = :updated_at
WHERE external_id = :eid
```

All placeholders (`:eid`, `:user_id`, etc.) are bound in application code; no string concatenation.

## Portability

- No Oracle-only SQL (e.g. no `NVL2`, `DUAL`-dependent logic, or proprietary hints) in the data access layer.
- If you switch RDBMS: keep the same `external_id` + numeric PK pattern; recreate DDL from `docs/ORACLE_SCHEMA.md` and `scripts/schema_oracle.sql` for the new dialect; change `DATABASE_URL` and driver.
