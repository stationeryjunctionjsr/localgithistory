# Oracle Schema – JSON to Table Mapping and Design Notes

## Design principles

- **Numeric PKs:** Every table uses `NUMBER GENERATED BY DEFAULT ON NULL AS IDENTITY` as primary key. Internal joins use this.
- **External ID:** `external_id VARCHAR2(32)` stores the legacy `_id` from JSON. Unique, indexed. **Never exposed as "database id"** – API continues to use `_id` (same value as `external_id`).
- **Foreign keys:** Use numeric `id` references (e.g. `user_id` → `sj_users.id`). Resolve `external_id` ↔ `id` in the DAO layer when reading/writing.
- **Indexes:** B-tree indexes on all FKs and on columns used in WHERE/ORDER (e.g. `email`, `status`, `created_at`). No over-indexing.
- **JSON/CLOB:** Used only for variable or nested structure: `address`, `device`, `items` (cart), `shipping_address`, `billing_address`, arrays of strings (e.g. `images` where not normalized).

## Column mapping (main entities)

### sj_users
- `id` (PK), `external_id` (UNIQUE), `user_id` (display number), `user_id_formatted`, `name`, `email`, `password_hash`, `role`, `phone`, `company_name`, `address` (CLOB), `saved_addresses` (CLOB), `is_active`, `approval_status`, `is_deactivated`, `credit_limit`, `credit_used`, `payment_terms`, `assigned_retailer` (external_id or NULL), `created_at`, `updated_at`.

### sj_orders
- `id` (PK), `external_id`, `user_id` (FK), `order_number`, `status`, `total`, `subtotal`, `tax`, `shipping`, `discount`, `order_type`, `payment_status`, `payment_method`, `upi_payment_screenshot` (CLOB), `shipping_address` (CLOB), `billing_address` (CLOB), `notes`, `printed_bill`, `assigned_valet` (external_id), `shipped_at`, `delivered_at`, `cod_*`, `decline_reason`, `cancelled_at`, `cancelled_by`, `turnaround_hours`, `created_at`, `updated_at`.  
- API still returns `user` as external_id (string). DAO resolves when loading/saving.

### sj_order_items
- `id` (PK), `order_id` (FK), `product_id` (FK), `quantity`, `price`.  
- API returns `product` as external_id; DAO resolves via sj_products.external_id.

### sj_sessions
- `id`, `external_id`, `user_id` (FK), `refresh_token_id`, `status`, `last_active_at`, `revoked_at`, `revoked_reason`, `device` (CLOB), `is_guest`, `comment`, `created_at`, `updated_at`.

### sj_carts
- `id`, `external_id`, `user_id` (FK), `items` (CLOB JSON – product, quantity, price, variantAttributes), `created_at`, `updated_at`.

## Oracle-specific choices (performance)

1. **IDENTITY columns** – Auto-increment PKs without explicit sequences; standard and portable.
2. **VARCHAR2(32)** for `external_id` – Fits hex IDs; indexed for lookups by `_id`.
3. **CLOB for JSON** – Works on all supported Oracle versions; use JSON type in 21c+ if you prefer (optional).
4. **TIMESTAMP for dates** – `created_at` / `updated_at` as `TIMESTAMP` for consistency and indexing.
5. **Indexes** – FK columns, `external_id`, `email`, `status`, `order_number`, `created_at` where used in filters/sorts. Single-column indexes only unless a clear multi-column query exists.
6. **Table prefix `sj_`** – Avoids reserved words (e.g. USER, ORDER, DATE).

## Portability

- No Oracle-only SQL in application code; standard SQL in DAO.
- Parameterized queries only (SQLAlchemy or bound parameters).
- If you move to another RDBMS: keep `external_id` and numeric PK pattern; re-create DDL from this mapping; swap dialect in connection config.
